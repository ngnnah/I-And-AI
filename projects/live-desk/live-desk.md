# Live desk

- The main session writes every reply to its live desk: a markdown file in `~/claude-replies/`, one per session, named `<YYYY-MM-DD>-<repo>-<topic>.md` with a kebab-case topic. Subagents don't. I read and answer it in MarkText. A session resumed from a handoff (below) continues its predecessor's file instead of starting one.
- Create the session's file on its first turn, before other tool work, with a Status whose Now says what you're starting on. Don't hold it back until you have an answer; with focus view on, the file is my only sign the session is working.
- Right after creating a session's file, open it once with `open -a MarkText ~/claude-replies/<file>`.
- The file has two parts, and they are its only H2 headings. At the top, `## Status · updated <MM-DD HH:MM>`, which you rewrite in place so it is always current. Below it, `## Log`: add each reply as a new entry at the bottom, `### <n> · <MM-DD HH:MM> · <short title>`, with any headings inside an entry at `####`. Never rewrite or reorder log entries.
- Status has, in this order: `### Now` (what you're doing this minute, or what you're waiting on me for); `### Open questions`; `### Next` (the steps left, each marked as mine or yours); `### Decisions` (one line each: the decision, why, who made it, its log entry); `### Done` (one line each, newest first, with its log entry). It holds only what's true now: drop finished steps from Next, move answered questions into Decisions, and rewrite a decision's line when it lands or changes (no "Proposed" left on something shipped). Status gets rewritten, so its items have no stable numbers: anywhere in the file, refer to them by their words, never "question 2" or "Next step 6".
- Update Status as you go, whenever part of it changes: a step finishes, a decision lands, the plan changes, a question comes up. During long work, don't go more than about ten tool calls without touching it; if I installed the nudge hook (`~/.claude/hooks/desk-nudge.sh`), it reminds you when you do.
- When you rewrite Status, keep every answer of mine in it you haven't answered yet, including one after `>>` at the end of a line.
- Write the file only with the Edit or Write tool, never through Bash (`cat >>`, `sed`, inline python): a Bash write needs my approval, and the prompt drags the VS Code panel to the bottom. Get the time from `date` before writing a heading or the Status line; never guess it and fix it afterwards.
- In chat, write one line: the gist plus a VS Code line link to the new entry's `###` heading, `[entry <n>](<the file's absolute path>#L<line>)`. Take the line number after the turn's last edit to the file, since Status edits shift it. MarkText can't be opened at a section from a link.
- Ask questions in the file, not with AskUserQuestion; its prompt drags the VS Code panel to the bottom.
- A question I send while you're working gets a one-line answer in chat at once, between tool calls, and the work carries on; the answer also goes in the next log entry. If answering takes research, give it to a background agent, keep working, and answer when it reports.
- My inline answers start with `>>`, either on their own line or at the end of the line I'm answering: `- >> yes` under a bullet, or `- Push it? >> yes` on the same line. A single `>` (or `> >`, as MarkText may save it) at the start of a line counts too. Never write a blockquote in the file yourself, and write `>>` yourself only inside backticks. At the start of each turn, find my answers with the grep below; a hit inside your own text (in backticks or a quote of my words) is not an answer. Then Read only Status and the lines around any new hit; read the whole file only on a session's first turn. Treat answers you haven't handled as part of my message, which may be just `>>`. When you wait on me (a run to finish, a step to take), ask me to send `>>`, never "r". In the new log entry, quote a few words of each answer you handle.
- Keep context clean: once a session has run about 15 of my turns, reached about 250k tokens of context, or had its context compacted, suggest continuing in a fresh session at the next natural break (work pushed, no agent running, nothing half-done). If I installed the nudge hook, it also reminds you, and shows me a line, when a session crosses 15 turns or 250k tokens. First add a log entry titled "Handoff": where things stand, what we tried and what surprised us (each with its evidence), uncommitted or unpushed work, running agents, open questions and any answer of mine still unhandled, my pending steps, and the first next step. The Handoff entry opens with the resume line, in backticks so I can copy it into the fresh session, naming that entry since a long desk can hold more than one: `Resume from the live desk ~/claude-replies/<file>, handoff §<n>`. Put the same line in Status → Now, and make it that turn's chat line, in backticks, with the entry link. Once a new session has picked the file up, the old session stops writing to it; until then, if I keep talking to the old session, it keeps the file and its Handoff current. The new session reads the whole file, checks `git status` and `git log` before trusting what it says, continues its log numbering, and still runs the repo's own handoff, if the repo has one.

Find my answers with:

```bash
grep -nE '^[[:space:]]*([-*+]|[0-9]+\.)?[[:space:]]*>|(^|[^`])>>' <file>
```
