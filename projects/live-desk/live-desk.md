# Live desk

- The main session writes every reply to its live desk: a markdown file in `~/claude-replies/`, one per session, named `<YYYY-MM-DD>-<repo>-<topic>.md` with a kebab-case topic. Subagents don't. A session on personal work (outside my work repos) keeps its desk in `~/claude-replies-personal/` instead, so personal desks stay out of any work sync; everything below applies to both folders. I read and answer it in Obsidian. A session resumed from a handoff (below) continues its predecessor's file instead of starting one, unless that Handoff moved to a fresh desk.
- Create the session's file on its first turn, before other tool work, with a Status whose Now says what you're starting on. If I installed the desk script (`~/.claude/bin/desk`), `~/.claude/bin/desk new <topic>` (with `--personal` for personal work and `--now "<text>"` for the first Now) creates it from the skeleton, opens it and prints its path; call `desk` by that path, which my allow rule matches. Don't hold it back until you have an answer; with focus view on, the file is my only sign the session is working.
- Right after creating a session's file, open it once with `open -a Obsidian ~/claude-replies/<file>` or `open -a Obsidian ~/claude-replies-personal/<file>`, matching where the desk lives (`desk new` already does); it opens as a tab in the Obsidian vault that holds the folder.
- The file has two parts, and they are its only H2 headings. At the top, `## Status · updated <MM-DD HH:MM>`, which you rewrite in place so it is always current. Below it, `## Log`: add each reply as a new entry at the bottom, `### @<n> · <MM-DD HH:MM> · <short title>`, with any headings inside an entry at `####`. Only headings use `@<n>`, so a search for `@<n> ` (with the space) lands on the entry; everywhere else, Status, the resume line and answer tags included, an entry is `§<n>`. Never rewrite or reorder log entries, except to tag my answers (below).
- Status has, in this order: `### Now` (what you're doing this minute, or what you're waiting on me for); `### Open questions`; `### Next` (the steps left, each marked as mine or yours); `### Decisions` (one line each: the decision, why, who made it, its log entry); `### Done` (one line each, newest first, with its log entry). It holds only what's true now: drop finished steps from Next, move answered questions into Decisions, and rewrite a decision's line when it lands or changes (no "Proposed" left on something shipped). Status gets rewritten, so its items have no stable numbers: anywhere in the file, refer to them by their words, never "question 2" or "Next step 6".
- Update Status as you go, whenever part of it changes: a step finishes, a decision lands, the plan changes, a question comes up. During long work, don't go more than about ten tool calls without touching it; if I installed the nudge hook (`~/.claude/hooks/desk-nudge.sh`), it reminds you when you do.
- When you rewrite Status, keep every answer of mine in it you haven't answered yet, including one after `>>` at the end of a line.
- Write the file only with the Edit or Write tool, never through Bash (`cat >>`, `sed`, inline python): a Bash write needs my approval, and the prompt drags the VS Code panel to the bottom. The one exception is `desk new`, which writes only a new file. Get the time from `desk check <file>` (below), or from `date` without the script, before writing a heading or the Status line; never guess it and fix it afterwards.
- A desk holds working notes only: never write keys, tokens, passwords or connection strings into it, nor query result rows or customer details (names, emails, phone numbers, addresses); give counts and table names instead, and say where the rows live. If I installed the nudge hook, it also refuses a desk write that looks like a key or holds an email address; it can't recognise query rows or names, so those rest on this rule.
- In chat, write one line: the gist plus a VS Code line link to the new entry's `###` heading, `[entry <n>](<the file's absolute path>#L<line>)`. Take the line number (`desk line <file> <n>`, if I installed the script) after the turn's last edit to the file, since Status edits shift it. `open -a` can't open the desk at a section.
- Ask questions in the file, not with AskUserQuestion; its prompt drags the VS Code panel to the bottom.
- A question I send while you're working gets a one-line answer in chat at once, between tool calls, and the work carries on; the answer also goes in the next log entry. If answering takes research, give it to a background agent, keep working, and answer when it reports.
- My inline answers start with `>>`, either on their own line or at the end of the line I'm answering: `- >> yes` under a bullet, or `- Push it? >> yes` on the same line. A single `>` (or `> >`, as some editors save it) at the start of a line counts too. Never write a blockquote in the file yourself, and write `>>` yourself only inside backticks. At the start of each turn, if I installed `desk` at `~/.claude/bin/desk`, run `~/.claude/bin/desk check <file>` as one call, never chained with other commands; it prints the time, my open answers (the grep below, unchanged) and Status's line numbers. Else run the grep below. The grep returns only answer lines with no ` ✓` tag, anywhere in the file, old entries included; never filter or trim its output, and read every hit plus Status. When an entry handles my answer, append ` ✓§<n>` (that entry) to the end of my line wherever it is, and to each line of a multi-line answer. In your own text, write `>>` only inside backticks and leave it out of quotes of my words, so your lines never show up as open. Treat answers you haven't handled as part of my message, which may be just `>>`. When you wait on me (a run to finish, a step to take), ask me to send `>>`, never "r". In the new log entry, quote a few words of each answer you handle.
- Keep context clean: once a session has run about 15 of my turns, reached about 400k tokens of context, or had its context compacted, ask me at the next natural break (work pushed, no agent running, nothing half-done) whether to continue in a fresh session; a Handoff written before I'm ready to switch goes stale and adds noise. If I installed the nudge hook, it also reminds you, and shows me a line, when a session crosses 15 turns or 400k tokens. Only once I agree, add a log entry titled "Handoff": where things stand, what we tried and what surprised us (each with its evidence), uncommitted or unpushed work, running agents, open questions and any answer of mine still unhandled, my pending steps, anything from earlier entries the next session still needs, and the first next step. When the desk has passed about 2,000 lines, the Handoff starts a fresh desk instead: a new file for the same work, dated today, whose §1 is the Handoff, with a short recap, a link to the old desk and "old §<n>" for its entries; the old desk ends with a one-line entry linking the new file, and the resume line names the new file. The Handoff entry opens with the resume line, in backticks so I can copy it into the fresh session, naming that entry since a long desk can hold more than one: `Resume from the live desk ~/claude-replies/<file>, handoff §<n>`. Put the same line in Status → Now, and make it that turn's chat line, in backticks, with the entry link. Once a new session has picked the file up, the old session stops writing to it; until then, if I keep talking to the old session, it keeps the file and its Handoff current. The new session reads Status, the named Handoff and everything after it (`desk line <file> <n>` or `grep -n '^### @<n> '` finds its line), and the lines around each open answer; it opens an older entry only when one of those points to it. It checks `git status` and `git log` before trusting what it says, continues its log numbering, and still runs the repo's own handoff, if the repo has one.

Find my open answers with:

```bash
grep -nE '^[[:space:]]*([-*+]|[0-9]+\.)?[[:space:]]*>[^✓]*$|(^|[^`])>>[^✓]*$' <file>
```
